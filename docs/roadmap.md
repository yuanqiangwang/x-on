# Roadmap — 候选清单与取舍

这份文档记录的是**待办与判断**，不是决策。决策记在 `docs/adr/`；这里记的是
"接下来值得做什么、按什么顺序、以及哪些东西我们明确不做"。

来源：2026-09-10 对 [asyar](https://github.com/Xoshbin/asyar)（Tauri v2 +
Svelte 5 的跨平台 Raycast 替代品）的通读与对比。asyar 是"平台级"产品——扩展生态、
AI/MCP、剪贴板、文件搜索；xon 是"把一件事做到极致"的 Windows 启动器。**定位不同，
所以可借鉴的是它的渲染生命周期与工程方法学，不是它的功能清单。**

---

## 一、渲染生命周期（来自 asyar 的 `launcher-rendering-lifecycle`）

asyar 的核心命题：**窗口几何与页面绘制绝不能不同步**。这与 ADR 0001 里"隐藏时
复位"解决的是同一类问题，但它做得更系统。下面三条按 ROI 排序，**都还没落地**。

### 1.1 resize 与 paint 对齐 + 失效代次

现状（`src/main.ts:280`）：

```280:281:src/main.ts
  const height = CHROME + (hasQuery ? GAP + rows * ROW_H : 0);
  win.setSize(new LogicalSize(640, height)).catch(() => {});
```

DOM 已经同步重建完，但 `setSize` 是异步 IPC → Rust → Win32。窗口可能**先长高、
内容后到**，露一帧空白；反过来则是"新内容被旧几何裁掉"。

要做的两件事（都便宜）：

- **resize 挂到下一帧**：`requestAnimationFrame` 之后再发 `setSize`，保证内容已进
  合成队列。
- **resize generation**：每次 resize 领一个递增代号，代号被超越的提交直接丢弃。
  这让"快速输入 / 连续 Esc-唤起"不会打出 `96→N→96` 的回弹。

40 ms 的 input debounce（`src/main.ts:372`）已缓解大部分，但**没解决最后一帧的
同步**——debounce 只减少次数，不保证顺序。

### 1.2 首帧预热

asyar 在 boot 时就预停（park）面板，让"第一次唤起"和"第 N 次唤起"走同一条路径。
xon 目前只预热了 emoji 字体（`src/main.ts:448`），**窗口本身从未被合成过**——
第一次 `Alt+Space` 要和 DWM + WebView2 的首次合成撞在一起。

做法：启动流程末尾加一次 `show()` → `hide()`（或至少一次 `setSize` +
`setFocus`）。成本几乎为零。

### 1.3 固定高度容器，减少 resize 的 relayout

asyar 把 WKWebView **钉死在最大高度**，窗口只做裁切，所以展开/收起**不触发任何
重排重绘**。

Windows 上 Tauri 的 webview 跟随窗口尺寸，无法完全照搬（真要裁切得上
`SetWindowRgn`，与 ADR 0001 的圆角/阴影方案冲突）。可以取一半：**给结果区一个
固定像素高度容器 + `overflow:hidden`**，让视口高度变化时内部布局不回流。

收益不如 macOS 上大，改动只在 CSS。

> ⚠️ 改 `ROW_H` / `CHROME` / `GAP` 时记得它们是手写的，与 `index.html` 的
> `--row-h` 和 padding 人工同步（见 `CODEBUDDY.md` 的 Gotchas）。

## 二、功能候选（按 ROI 排序）

判据：**是否让"每天都会打开它"这件事更成立**。纯前端、不新增依赖、不破坏
"单窗口无框架"定位的优先。

| # | 候选 | 判断 | 理由 |
| --- | --- | --- | --- |
| 1 | **计算器** — 输入 `1+2*3` 直接出结果行 | ✅ 强推 | 纯前端，不碰后端。asyar 用 "Reactive Live Subtitle" 把公式结果实时写进结果行副标题；xon 已有 `subtitle()`（`src/main.ts:143`）这套机制，直接复用 |
| 2 | **URL / Portal 直达** — 输入含 `.` 或 `http` → 浏览器打开 | ✅ 强推 | 十几行，每天都会用到 |
| 3 | **路径直达** — `C:\Users\...`、`~` 展开 → 打开 | ✅ 推荐 | 同上，复用已有的 `opener` 链路 |
| 4 | **PATH 命令检索**（`calc` / `mstsc` / `devmgmt.msc`…） | ✅ **已落地** | 见下方「第五类数据源：PATH 命令」 |
| 5 | **使用频率 / 最近使用加权排序** | ✅ 推荐 | asyar 没强调，但 Raycast/Alfred 都有。当前是纯名称打分（`matcher.ts`），加一个 `launchPath → {count, lastUsed}` 的本地 JSON 权重，体感提升最明显 |
| 6 | **HUD 通知** — 自动消失的轻提示（"已复制"） | ⚠️ 待评估 | 需要第二个 frameless 窗口，与 ADR 0001 的取舍相关；或在窗口内做一个顶层 toast 条 |
| 7 | **Context Modes** — 前缀切换模式（chip 提示） | ⚠️ 待评估 | 等 #1~#3 落地后，自动嗅探会开始打架，那时再要前缀隔离 |
| 8 | **剪贴板历史** | ⚠️ 中成本 | 别抄它的实现，抄它的**分层隐私设计**：捕获时按源排除 → 正则脱敏 → 本地加密 → 最小化同步。前两层在 Rust 侧几十行就能有 |
| 9 | **文件搜索** | ❌ 暂缓 | asyar 的 `file-search.md`（arena 索引 + 并行 walker + 合并 watcher）写得很漂亮，但对"应用启动器"定位是把复杂度翻倍的活 |
| 10 | **命令直通**（输入任意命令带参执行，如 `ipconfig /all`） | ⏸ 后续 | 见下方「为什么先做检索不做直通」 |

### 第五类数据源：PATH 命令（已落地）

索引原本只有四类：开始菜单 `.lnk`、便携应用、系统功能、Store 应用。前两类带英文
别名（`.lnk` 的 stem），后两类**只有本地化中文名**——于是 `calc` 搜不到「计算器」，
`devmgmt.msc` 这类开始菜单根本不提供的入口更是完全不可达。

`src-tauri/src/commands.rs` 补上了第五类。核心设计是**能补别名就补别名**：

- 前四类已有同名条目 → **只往它身上补英文别名**，不新增行。所以 `calc` 命中的
  仍是 Store 那一行（保留 UWP 图标、走 AUMID 激活），列表里不会出现两个「计算器」。
- 索引里没有的 → 才新增一行，且存 **PATH 解析出的完整路径**（不是裸命令名），
  这样 `SHGetFileInfoW` 能取到图标；本机解析不到的命令自动跳过，因此家庭版没有
  `gpedit` 这类差异无需维护两份清单。

实测分布（本机 Win11 家庭版，37 条命令全部可解析）：

- **补别名 24 条**：计算器、记事本、画图、截图工具、任务管理器、命令提示符、
  Windows PowerShell、注册表编辑器、文件资源管理器、控制面板、服务、事件查看器、
  计算机管理、任务计划程序、系统配置、系统信息、资源监视器、性能监视器、磁盘清理、
  远程桌面连接、字符映射表、屏幕键盘、放大镜、步骤记录器
- **新增 13 条**：Windows 终端、设备管理器、磁盘管理、高级安全 Windows 防火墙、
  证书管理器、磁盘碎片整理、DirectX 诊断工具、音量合成器、Windows 版本信息、
  程序和功能、系统属性、网络连接、电源选项

只净增 13 行，搜索结果几乎没有被稀释。`.msc` / `.cpl` 的图标也已验证能正常提取。

**维护约定**：`COMMANDS` 里 `name` 的取值必须和 Windows 自己的显示名一致
（"计算器"不能写成"计算器应用"），否则匹配不上、会白白多出一行。表内新增项后跑
`cargo test commands::` 看 `alias-only` / `new rows` 两个诊断输出，确认分类符合预期。

### 为什么先做检索、不做直通

「输入任意命令带参执行」（`ipconfig /all`）暂缓，因为它的取舍和检索完全不同：

- **需要预判输入是不是命令**：要么启动时扫 PATH 建一个可执行文件集合（几千个名字、
  约 100 KB，一次性发给前端），要么每次输入都回后端查一次（会吃掉按键路径的预算）。
- **会与开始菜单 .lnk 撞车**：`notepad` / `python` / `code` 既是 PATH 命令、又有
  英文别名精确命中。需要一套排序规则（含参数时置顶、有强应用匹配时不显示）。
- **破坏性命令无护栏**：`shutdown /s /t 0` 误按回车就执行，而启动器正是"随手回车"
  的场景。

等检索这层用一阵、确认命令条目的收录边界合适了，再上直通。

## 三、明确不做（以及为什么）

写下来是为了**避免以后重新讨论一遍**。

- **扩展系统 / iframe 沙箱 / 扩展商店** — asyar 的核心差异化，代价是 2272 commits、
  monorepo 四包、GPL/MIT 拆分授权。而且它自己的审计报告承认：435.6 MB 内存、
  3.2% 闲置 CPU、一个失控的定时扩展能造成 8640 次 fsync/天。**功能越多越重，这
  恰恰反证了 xon 的"单窗口、无框架、无宿主"是优势。**
- **AI / MCP** — 同上，且引入网络与密钥管理，与"本地优先、离线可用"冲突。
- **换成 Svelte / React** — 坚持无框架是刻意的，不为对齐技术栈而换。
- **"unthrottled parked webview"**（隐藏时保持 alpha=0 常驻，换取 12–17 ms 显示）
  — 需要分层透明窗口，与 ADR 0001 的不透明决策直接冲突；asyar 自己承认代价是
  0.3–0.4% 闲置 CPU + **1.4 MB/h 且无平台期的内存爬升**。不划算，且 Windows 上
  实现路径不同。
- **多窗口（main / settings / hud）** — asyar 因此常驻 3 个 WebContent 进程，
  固定 ~160 MB 税。单窗口是对的。
- **真 Acrylic 毛玻璃** — 已在 ADR 0001 评估，需重做渲染层，留二期。
- **原生右键菜单** — 已在 ADR 0001 记录实验与回退结论（越界能力与视觉一致性
  二选一，当前选后者）。

## 四、不要被反向优化的地方

对比中发现 **xon 已经比 asyar 做得好的两处**，记录在此防止"看别人有就觉得自己缺"：

- **手写的 `Debouncer`**（`src-tauri/src/lib.rs:924`）比 asyar 强。它是阻塞
  `recv_timeout(400ms)`，空闲时线程完全休眠、零开销；asyar 的闲置审计报告里
  排名第 2、第 3 的开销来源正是 `notify-debouncer` 的 125 ms 空转 tick（"空闲时
  也在分配两个 HashMap"）。**这条不用改。**
- **`ConfigWatcher.own_write` 防自写回环**（`persist_settings` 记录自身写入文本）
  — asyar 需要靠"写入合并"提案来治的病，xon 从设计上就没有。

## 五、性能预算

`benchmarks/` 建立之前的 README 写的是 "sub-millisecond response times"——
无法复现，也无法证伪。现在的规则：

> **任何性能主张，必须有一条能把它重新打印出来的命令。**

- 测量方式见 [`benchmarks/README.md`](../benchmarks/README.md)，命令是
  `npm run bench`。
- 两个预算是分开的：**hotkey → visible** 和 **keystroke → results**。后者包含
  40 ms debounce + 全量列表重建 + 图标 IPC 回灌（`src/main.ts:347`），通常比前者
  慢数倍——**用户搜索时感受到的是后者**。只优化前者对体感毫无帮助。
- 若某次改动让 p50 变差超过 ~3 ms（轮询分辨率），先看是不是同一个会话、同一台
  机器上的回归，再下结论。

## 六、基线（2026-09-10，已测）

Windows 11 / Core Ultra 7 255H / xon 0.6.0 release：

| | p50 | p95 |
| --- | --- | --- |
| Hotkey → visible | **8.9 ms** | 14.6 ms |
| Keystroke → results | **63.3 ms** | 72.5 ms |

> 这组数字**已包含第五类数据源（PATH 命令）**：索引净增 13 个新条目、另给 24 条
> 已有条目补了英文别名。keystroke p50 与加入前（65.6 ms）持平，证明命令数据源
> 没有稀释搜索、没有拖慢渲染。

闲置：0.21% CPU；进程组递归 7 个进程，**私有内存 273.1 MB、工作集 520.6 MB**；
安装器 1.58 MB。

**内存构成值得单独记住**：278 MB 里 xon 主进程只占 **19 MB**，其余 259 MB 是
六个 `msedgewebview2.exe`。也就是说"轻量"指的是 Rust 侧那 19 MB，WebView2 是
Windows 上跑 webview UI 的固定税——换任何前端框架都改变不了它。

含命令数据源后，连跑多次 hotkey p50 稳定于 8–9 ms、keystroke p50 稳定于
63–66 ms —— 数字可复现。完整样本见 `benchmarks/results/latest.md`。

**基线给出的三个结论，直接决定下面的顺序：**

1. **唤起路径已经不是瓶颈**（8.6 ms，优于 asyar 自测的 12–17 ms）。所以 1.1
   （resize 与 paint 对齐）的价值不在"更快"，而在"不抖"——它消除的是偶发的
   空白/裁切帧，不是平均值。1.2（首帧预热）同理：它管的是**第一次**唤起，
   而基线里 25 次唤起是稳态值。
2. **真正的体感延迟在按键路径**（66.8 ms，约为唤起的 8 倍），其中约 40 ms 是
   `main.ts` 里固定的 input debounce。**要动体感，先动这里**——比如下调
   debounce，或让首屏 10 行先渲染、图标异步补。
3. **闲置成本已经很低**（0.31% CPU），不要为它做无谓优化。内存那 278 MB 里
   259 MB 是 WebView2 的固定开销，不是 xon 能优化的部分。

## 七、建议的执行顺序

1. ~~跑基线~~ ✅ 已完成，见上。
2. **按键路径（66.8 ms）**——评估 debounce 从 40 ms 下调，以及图标 IPC 是否阻塞
   首屏渲染。这是唯一能明显改变体感的一项。
3. 第一章的 1.1 + 1.2（resize 对齐 + 首帧预热）——消除偶发抖动与首次唤起的
   冷合成，改动小。
4. 第二章的 #1~#4（计算器 / URL / 路径 / 系统命令）。
5. 第二章的 #5（频率权重排序）。
6. 每步之后重跑 `npm run bench` 对比，别凭感觉判断"变快了"。
