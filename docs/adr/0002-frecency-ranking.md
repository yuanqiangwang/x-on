# ADR 0002 — 个人化排序：frecency 权重与存续策略

- **Status**: Accepted（2026-09-10）
- **Date**: 2026-09-10
- **Last reviewed**: 2026-09-10

## Context

### 问题：同层并列时排序是随机的

`matcher.ts` **决策前**是纯名称打分：7 层 tier（精确 > 名称前缀 > 全拼前缀 > 词首缩写 >
声母前缀 > 子串 > 子序列），同一 tier 内按 `len`（查询覆盖字段的比例）排序（当时的
排序键）：

```ts
    pool.sort((x, y) => x.tier - y.tier || x.len - y.len);
```

`len` 也相同时，落到 JS stable sort 的插入序 —— 也就是 `build_index`（`lib.rs:412`）的
爬取序。WalkDir 的顺序取决于文件系统，**实际近似随机**，每次重扫或重启都可能变。

这不是边缘情况，而是拼音首字母查询的常态。输入 `js`：

| 条目 | init | tier | len |
| --- | --- | --- | --- |
| 计算器 | `jsq` | 5 | 3 |
| 记事本 | `jsb` | 5 | 3 |
| 计算机管理 | `jsjgl` | 5 | 5 |

前两者 tier 与 len 完全并列 → 排序随机。`js` / `zg` / `tx` 这类查询都会撞上，
所以"日常查询里相当一部分的先后顺序是随机的"。

### 数据形状（决定存续策略）

要持久化的只有 `launchPath -> {count, lastUsed}`：

| 维度 | 实际 |
| --- | --- |
| 规模 | 只有"真的启动过"的条目有记录，几十~几百行 |
| 读 | 前端要**全量**（matcher 要给每个候选打分） |
| 写 | 每次启动 upsert 一行，而启动是用户主动动作 |
| 并发 | 无 —— `tauri-plugin-single-instance` 保证单进程 |

即"全量载入内存 + 低频单行 upsert"。

### 参考模型

输入法的用户词典与本场景同构，沿用它的三条原则：
静态词频为骨架、用户词频是**叠加其上的有界修正**；**只从"上屏"学习**；
用户数据**独立成文件、可重置**。

## Decision

### 1. 权重只做末级破平，不得跨 tier

排序键固定为：

```
tier -> len -> frecency
```

frecency 只在 tier 与 len 都相同时才起作用。

> **红线：任何个人权重都不能把精确命中（tier 1）或名称前缀（tier 2）挤下去。**
> 用户打了全名就必须第一 —— "这个启动器在跟我作对"是不可接受的失败模式。

### 2. 只从"上屏"学习

只有启动**成功后**才记录一次。`Enter` / `Ctrl+Enter` / `Alt+序号` / 鼠标点击都算；
悬停、高亮、仅仅出现在列表里都不算（不从曝光学习）。

### 3. 权重形态：分桶衰减 + log(次数)

按时间分桶（今天 / 本周 / 本月 / 更早）各给基准分，再乘以 `log(次数)`。理由：

- 整数、可读、可被用户直接查看与手改 —— 与本项目"数据文件可见"的风格一致；
- 抗系统时钟回拨（连续指数衰减会产生诡异排序）；
- 天然有界，便于按条目数裁剪。

### 4. 存续：独立 `usage.json` + 原子写

- **不复用** `settings.json` / `apps.json`，新开 `usage.json`（沿用"一个文件一个职责"）；
- 复用 `portable.rs` 的 `manifest_path / load / save` 模式（`portable.rs:30-54`），
  并补上**原子替换**（写临时文件 + rename）；
- **裁剪**：按条目数上限淘汰（如 200）；读取时忽略索引里已不存在的 `launchPath`，
  写回时顺手清理。

### 5. 不碰热键链路

- **写**：`launch_app` 成功之后起后台线程 upsert，绝不在按键路径上写盘；
- **读**：一次性全量载入内存，前端拿一份**权重快照**，不暴露任何查询接口；
- **`matcher` 保持纯函数**：权重从外部注入（`AppInfo` 字段或独立的 weights map），
  **不能让 matcher 自己去读文件 / 查存储** —— 否则现在"可注入 `Syllabize` 做确定性
  单测"的设计就废了。

### 6. 必须有复位出口

排序会随时间漂移。必须提供"清空使用记录"的入口（托盘项或配置开关），
否则用户遇到排序错乱时无从复位。

### 7. 键：`launchPath`

与 icon cache（`main.ts:227`）同一把键。已知损耗：`.lnk` 重装后路径可能变、
便携 exe 移动位置会丢历史。**接受**，不为此加 `targetPath` 回退键。

### 8. 不做数据库（2026-09-10 评估）

评估后**不引入** SQLite / 嵌入式 KV：

- 该 workload 用不到数据库的任何能力：无索引需求、无部分查询、无并发；
- 代价可量化：新增 C 工具链依赖（现在 `Cargo.toml` 是纯 Rust 依赖）、
  二进制约 +1 MB，而安装包基线只有 **1.58 MB**（量级上接近翻倍）、
  为一张三列表引入 schema 版本 / migration 机制；
- `tauri-plugin-sql` 会把 SQL 推给前端，与本项目"前端只消费排好序的结果、
  全部策略藏在模块内"的分工冲突。

> **重新评估的触发条件**：roadmap 第二章 #8（剪贴板历史）或 #9（文件搜索）真要开工时。
> 那才是结构化存储的真实用户 —— 届时把 `usage` 这张表一并迁入即可，迁移成本极低。

## Consequences

- ✅ 同 tier / 同 len 的随机排序变成稳定且符合个人习惯；拼音首字母查询（`js` 这类）
  直接受益。
- ✅ 冷启动无数据时行为与现状完全一致（优雅降级）。
- ✅ 存续层是纯 JSON、零新依赖，与项目既有取舍一致。
- ⚠️ 排序会随时间漂移 —— 是特性也是困扰，因此依赖第 6 条的复位出口。
- ⚠️ 重装 / 移动会丢历史（第 7 条）。
- ✅ 空态「↓ 展开常用列表」已闭环：`browsing` 状态 + `matcher.frequent()`，
  后者现在按权重降序切片；无使用数据时因稳定排序退化成索引序。
- ⚠️ **已知局限（2026-09-10 评估，暂不处置）**：缩写查询里"拉丁词首缩写"
  （tier 4，`words`，如 Docker Desktop → `dd`）与"中文拼音声母"（tier 5，`init`，
  如 钉钉 → `dd`）被拆成两层，拉丁恒定优先 —— 于是权重在这类碰撞上**永远轮不到
  比较**。实测：`dd` 恒先出 Docker Desktop，哪怕钉钉已有使用记录。
  根因是这两者本是**同一概念在两种文字上的形态**，分成两层没有质量依据。
  处置：**暂不合并**。合并（7 层 → 6 层）会让"无使用数据期"的这类并列退回索引序，
  确定性短期下降；且多 token 的中文名（`微信 开发者工具` → `wk`）与单 token 中文名
  （`微科` → `wk`）之间也有一类先后被拉平。先攒使用数据、让大部分缩写歧义已有权重
  裁决之后，再评估合并。

## 备选路径（均未采用）

- **让权重跨 tier 冒头**：破坏"打全名必第一"的确定性，否决。
- **连续指数衰减**：不可读、不可手改、怕时钟回拨 → 用分桶替代。
- **数据库（SQLite / redb / tauri-plugin-sql）**：见 Decision 第 8 条，留待 #8 / #9。
- **WebView `localStorage`**：游离在配置目录之外、清缓存即丢、不可统一管理，
  与本项目"数据文件集中在配置目录、可见可改"的风格不一致。
- **写入放在热键链路**：按键是高频路径，不接受。
